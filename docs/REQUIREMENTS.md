## 3. Логика подсчёта (pipeline из 4 шагов)

| Шаг | Статус | Реализация |
|---|---|---|
| 1. Получить схему GraphQL | ✅ | introspection при старте/SDL/API, снапшоты в `schemas/` |
| 2. Принять запрос от тестовой машины | ✅ | `/proxy`, контекст прогона из заголовков |
| 3. Распарсить AST и связать со схемой | ✅ | `analyzeDocument` + `graphql.validate` |
| 4. Обновить метрики и отдать запрос дальше | ✅ | `repository.applyCoverage` → `coverage/<run>.json`, ответ upstream 1:1 |

| Разрез | Статус | Реализация |
|---|---|---|
| schema coverage | ✅ | `summary.fieldsPercent` — всё, что видел трафик |
| test coverage | ✅ | `summary.testCoverage` — только поля, задетые именованными тестами |

## 9. Ограничения

| Ограничение | Что делать |
|---|---|
| WebSocket-подписки не проксируются | HTTP/SSE поддерживаются; для WS — отдельный gateway или расширение прокси |
| Batch-запросы отклоняются (400) | отправлять по одному запросу |
| Один активный снапшот в UI | переключение через «Схема»; API умеет `schemaId` |
| In-process хранилище, один инстанс | для нескольких реплик — внешняя БД (см. `docs/ARCHITECTURE.md`) |
| Эфемерный диск на free-плане Render | persistent disk + `DATA_DIR=/var/data` |
| Журнал ищется за `EXECUTION_LOOKBACK_DAYS` | увеличить переменную |
| GitLab CI без готового шаблона | использовать `/api/ingest` (пример в `docs/DEPLOY.md`) |
